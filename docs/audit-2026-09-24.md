# Platform audit — 24 September 2026

## Remediation status

The application findings below were repaired and deployed on 24 September 2026. Regression coverage now includes the public JSON boundary, director priority preservation, reservation cleanup, atomic offer creation, manual suspension/reinstatement, group-age validation, healthy capacity scanning, historical attendance, final statuses, correction-state filtering, SMS job claiming, server-side registry pagination, and a real two-process last-place allocation test. The final isolated suite passed **90 tests / 405 assertions**. The current lockfile also passes `npm audit` with **0 reported vulnerabilities**, and the production frontend build completes successfully. Large-scale HTTP load testing remains separate capacity work rather than a code-correctness test.

## Scope and evidence

Reviewed registration and validation, role boundaries, capacity and waiting-list workflows, offers, attendance and reinstatement, annual porting, notification delivery, audit logging, quality scanning, frontend dependencies, and VPS service configuration. This is a code and existing-test audit, not an exhaustive penetration test or a concurrent load test.

- VPS suite: **82 tests passed, 373 assertions**. Its test bootstrap rejects database names not ending in `_testing`; `phpunit.xml` selects `bagebi_testing`.
- Eight key workflow/controller files were SHA-256 matched between workspace and VPS.
- VPS `bagebi-queue.service` and `bagebi-scheduler.service` are active. Scheduling lists waiting-list processing every ten minutes, attendance at 20:00, and quality scanning at 01:30. Active services and listed schedules do not by themselves prove every historical execution succeeded.
- Production PHP dependency audit: no advisories or abandoned packages reported.
- Local frontend dependency audit: 212 affected dependency entries — 6 critical, 57 high, 139 moderate, 10 low. Includes development/transitive dependencies; not 212 proven remotely exploitable application vulnerabilities. Direct flagged packages include axios, lodash, postcss, react-scripts and vue-template-compiler.
- A database-free probe against the installed Laravel Request implementation confirmed that removing fields from `$request->request` does not remove them from JSON input.
- No production exploit requests, SMS sends, registration submissions, data fixes, or deployment were performed for this audit. Application source was not changed.

## Findings in repair order

### 1. Critical: public JSON registration can reach the existing-child edit path

`app/Http/Controllers/API/KindergartenerController.php:59–62, 85, 130, 162`

`publicStore()` removes `id` and `has_permission` only from the form parameter bag before calling the shared `store()`. JSON input survives: the isolated Request probe returned both supplied values after removal. The shared method reads `$request->id`, loads an existing child, excludes that ID from uniqueness validation and saves the submitted data. Its access check only runs for authenticated directors. While registration is open, a crafted unauthenticated JSON request can therefore enter the update path, subject to ordinary field validation. JSON `has_permission` also permits an applicant to claim approved priority.

Repair: use a dedicated create-only public validation/input allowlist and explicitly server-set priority approval. Never accept a public record ID. Add unauthenticated JSON regression cases; do not verify by modifying real children.

### 2. High: director edits can erase approved priority

`app/Http/Controllers/API/KindergartenerController.php:82–83, 175–198`

For a normal director form submission, priority fields are removed. The later shared priority handler interprets the missing field as a request to delete the existing priority. Editing a name or phone can consequently remove approved priority and reset waiting-list rank to 999. JSON also bypasses the intended priority-field removal.

Repair: execute priority mutations only in the union-admin path; preserve the existing priority for director edits. Test both form and JSON submissions.

### 3. High: deleting an offered child leaks a reserved place

`app/Http/Controllers/API/KindergartenerController.php:312–330`

Deletion calls the workflow only for enrolled or suspended children. A child with an active placement offer remains `waiting`, so deletion skips `closeWaitingEntry()`. Cascading deletion removes the entry and offer but does not decrement `space_reserved`. The place remains unavailable and can block annual porting.

Repair: lock and clean up every active placement/queue reservation in the same transaction as deletion. Test deleting an offered waiter and confirm the next waiter can receive the place.

### 4. High: offer creation and notification enqueue are separate commits

`app/Console/Commands/ProcessWaitingList.php:23`

The reservation, queue state and offer are committed before `ParentNotificationService::send()` and audit creation. If the process stops or enqueueing fails in that gap, the next scheduler run skips the now-offered entry. A reservation can expire without any SMS job being created. Only the token hash is stored on the offer; the raw token exists in the interrupted process until the notification link is persisted.

Repair: persist the offer, durable notification payload/job and audit together, or use a transactional outbox with recovery. Test a simulated enqueue failure.

### 5. High: manual suspension has no reinstatement deadline or upload request

`app/Http/Controllers/ApplicationStatusController.php:20–21`; `app/Http/Controllers/API/KindergartenerController.php:367–375`; `app/Console/Commands/EvaluateAttendance.php:20`

Manual and bulk suspension call `transition()` and send a generic status SMS. Only the attendance command creates the five-working-day reinstatement request and upload link. Manually suspended children retain their seat but have no equivalent document/deadline process. If manual suspension is intended to follow the stated suspension rules, this is a missing workflow branch; otherwise the distinction needs an explicit business rule and UI explanation.

### 6. Medium: child age is not checked against the selected group

`app/Http/Controllers/API/KindergartenerController.php:105–151`

Validation checks age 2–6 at school start and whether the selected group belongs to the garden, but never compares age with that group's range. An age-eligible two-year-old can be placed in a 5–6 group through the backend. Municipality is only required, not validated against the garden's municipality.

Repair: validate the garden/municipality/group relationship and selected age range on the server; explicitly define exceptions for mixed-age groups.

### 7. Medium: quality scanner reports valid capacity and graduates as errors

`app/Services/DataQualityScanner.php:81–83, 154`

The operational model stores `space_free = limit - occupied`; reserved seats are deducted when calculating availability. The scanner expects `limit - occupied - reserved`, falsely flagging a consistent group whenever it has reservations. It also flags a missing group for all children, although annual porting intentionally clears the group of graduates.

Repair: share the capacity invariant and apply status-aware validation. Add healthy reserved-capacity and correctly graduated-child fixtures.

### 8. Medium: historical attendance corrections overwrite group history

`app/Http/Controllers/AttendanceController.php:87–91`

Updating an old attendance record assigns the child's current `group_id`. After annual porting or a transfer, correcting an old note/status can move that historical record into the new group and distort reports. The index also filters historical rows using the child's current placement.

Repair: preserve existing attendance placement metadata and define historical roster selection separately from the current roster.

### 9. Medium: sensitive manual overrides do not require a reason; some audit failures are ignored

`app/Http/Controllers/ApplicationStatusController.php:11`; `app/Http/Controllers/API/KindergartenerController.php:367–375`; `app/Http/Controllers/Controller.php:15–35`

Manual enrollment can bypass an existing queue without a required explanation. The status endpoint accepts a nullable reason, while bulk updates record the generic `Bulk status update`. Many child/user/garden changes call optional audit logging after persistence; audit-write failure logs a warning and still reports success. Garden capacity updates log name/municipality rather than before/after capacity values.

Repair: require reasons for queue/status exceptions and make critical changes and their detailed audit records atomic.

### 10. Medium: final status fields can contradict one another

`app/Services/ApplicationWorkflowService.php:88–93`; `app/Http/Controllers/ApplicationStatusController.php:11`

The status endpoint accepts `graduated`, but ordinary transition does not set `graduate` or clear the group as annual porting does. Conversely, changing a previously graduated child's placement can assign an active status while leaving `graduate = true`. This affects editing, quality reports and future porting.

Repair: define legal transitions and maintain the final-state fields together, including explicit reactivation rules.

### 11. Medium: “needs correction” filter cannot find requests returned for correction

`app/Http/Controllers/ReinstatementController.php:48–60`; `resources/views/reinstatement/index.blade.php:6`

Review accepts `needs_correction` but saves the request as `pending`. The list offers a `needs_correction` filter and queries that exact status, so the administrator cannot retrieve returned requests using it. Expiry currently handles pending/no-document requests; changing the stored state requires adapting expiry as well.

Repair: model the correction state consistently across review, upload, list and expiry.

### 12. Medium: SMS retry has no application-level already-sent guard

`app/Notifications/ParentSmsNotification.php`; `app/Notifications/Channels/SmsOfficeChannel.php`; `app/Http/Controllers/OperationsController.php:37–59`

The failure listener marks delivery failed on each thrown attempt, allowing manual resend while the original job may still retry. Neither the notification nor channel checks whether that delivery was subsequently sent. Multiple jobs for one delivery can call the provider. A stable provider reference is supplied, but provider-side deduplication was not verified and should not be assumed.

Repair: distinguish retrying from terminal failure and coordinate jobs per delivery; check provider status for ambiguous network outcomes.

### 13. Medium: large registries are loaded entirely into the browser

`app/Http/Controllers/API/KindergartenerController.php:38–42`; `resources/views/kindergarteners/list.blade.php`

The list loads all scoped children and related models with `get()`, then serializes them for client-side DataTables. Visible pagination does not reduce database fetch size or response payload. Growth increases page load time and exposes all fetched model fields to the authorized page even when some columns are hidden.

Repair: select necessary fields and add server-side search/pagination while retaining role scoping.

## Test and maintenance gaps

- `CapacityLogicTest::test_last_place_is_not_allocated_twice` performs two sequential calls, not concurrent transactions. Passing it is not evidence of race-free behavior under load.
- Current tests do not cover the public JSON update bypass, director priority preservation, offered-child deletion, offer/outbox interruption, or healthy reserved-capacity scan.
- Long-running workflows acquire capacity, child, queue and offer locks in different orders. Assess actual deadlocks using isolated concurrent tests; this review did not reproduce one.
- Frontend dependencies need a staged update/removal review. Do not run a forced blanket dependency upgrade; it can break React registration and the build.
- The working tree contains many modified/untracked application files and generated assets, and tracked `node_modules` files. A reproducible release needs a reviewed source snapshot and clean build inputs.
- Automated tests do not establish full visual, keyboard, CSP or device compatibility. This audit did not repeat a screen-by-screen browser review.

## Recommended sequence

1. Close the public create/update boundary and protect director priority edits; add regression coverage.
2. Repair reservation cleanup and atomic offer/notification/audit persistence.
3. Clarify manual suspension, correction and final-state transitions; enforce group/age validation.
4. Correct quality checks and historical attendance behavior.
5. Add failure-injection/concurrency coverage, then address dependency and registry scaling work.

No claim is made that passing the current suite eliminates the findings above. No application fixes are included in this audit.
